# ADR-0016: Writes across PostgreSQL and MongoDB

- Status: Proposed
- Type: technical
- Date: 2026-10-24
- Issue: #176

## Context

PostgreSQL is the source of truth and MongoDB holds lap records and running order history; there are no transactions across the two (ADR-0002). Several use cases change both (`docs/design/database.md`):

| Use case | PostgreSQL | MongoDB |
| --- | --- | --- |
| Submit, edit, or delete lap times | The member's average time and lap count | `lap_records` |
| Remove a runner from a confirmed running order (attendance change, cancelled invitation, leaving, editing the order) | The running order; then the member's average time and lap count | Delete the member's `lap_records` for the race |
| Change a running order | The running order | A snapshot in `running_order_history` |

If the second write fails after the first succeeded, the stores disagree: for example a runner is removed but their laps remain and still count in their average. These changes affect members' records directly, so a failure must not leave them silently wrong. ADR-0011 left the order and the failure handling to the implementation; this ADR sets one rule for all of them.

## Decision

**Every use case that writes to both stores records the remaining work in PostgreSQL first (an outbox), and the work is completed by the request or, if that fails, by a retry worker.**

**Steps**

1. **One PostgreSQL transaction** writes the PostgreSQL changes of the use case (if any) **and an outbox row** that lists the remaining steps in order (for example: delete the laps of member M in race R, then recalculate M's average).
2. **The MongoDB steps** run after the commit. Each one is idempotent — running it twice has the same effect as running it once:
   - Documents are written by IDs generated by the application (UUIDv7, `shared.IDGenerator`), as upserts.
   - Deletes are by key (member and race), so deleting again does nothing.
3. **The final PostgreSQL step** (for example updating the average time) runs **in one transaction that also deletes the outbox row**. Because the update and the removal of the row commit together, the update is applied exactly once, even if the step is retried. The average formulas in `docs/design/database.md` stay as they are.

**Retries**

- The request runs steps 2 and 3 right after step 1. If they fail, the outbox row stays.
- A retry worker in the backend process picks up outbox rows that are not done, with increasing delays between attempts. It locks rows with `FOR UPDATE SKIP LOCKED`, so more than one backend process can run it safely.
- After a set number of failed attempts, the row is kept and an error is logged (`log/slog`) so it can be looked at; it is never dropped silently.

**Responses**

- Once step 1 commits, the change is accepted and the API responds with success. Reads may show the previous state until steps 2 and 3 finish, normally within the same request.

**Layers (ADR-0011)**

- Use cases add outbox entries through an Application interface, in the same unit of work as their repository writes.
- Infrastructure stores the outbox in a PostgreSQL table, runs the MongoDB steps, and runs the retry worker. How the PostgreSQL transaction is shared between repositories is decided with the database access (ADR-0015).

## Alternatives considered

| Option | Why it was not chosen |
| --- | --- |
| Fixed order, log failures, fix by hand | A failure leaves the stores disagreeing silently until someone notices; laps of a removed runner would keep counting in their average |
| Undo the first write when the second fails (compensation) | The undo can also fail, so a record of unfinished work is needed anyway |
| Move lap records and history to PostgreSQL | Removes the problem, but reverses ADR-0002's decision to keep append-only and document-shaped data out of the relational schema |
| Distributed transactions across the two databases | Not supported between PostgreSQL and MongoDB, and far heavier than tasuki needs |

## Consequences

- The two stores always end up consistent, even when MongoDB is briefly unavailable.
- There is a new PostgreSQL table (the outbox) and a background worker in the backend; the table is added to `docs/design/database.md` when this is implemented.
- Every MongoDB step must be written to be idempotent, and every final PostgreSQL step must delete its outbox row in the same transaction. Reviews check both.
- For a short time after a successful response, other screens may show the previous state (for example an average not yet updated). The frontend refetches after a change (ADR-0013), so this is normally not visible.
- Outbox rows that keep failing need someone to look at the logs; how that is noticed in production is decided with hosting (ADR-0018).

# ADR-0016: PostgreSQL と MongoDB をまたぐ書き込み

- Status: Proposed
- Type: technical
- Date: 2026-10-24
- Issue: #176

## Context（背景）

PostgreSQL が正で、MongoDB はラップの記録と走順の履歴を持つ。2 つをまたぐトランザクションはない（ADR-0002）。いくつかのユースケースは両方を変える（`docs/design/database.md`）：

| ユースケース | PostgreSQL | MongoDB |
| --- | --- | --- |
| ラップタイムを足す、直す、消す | メンバーの平均タイムとラップ数 | `lap_records` |
| 確定した走順から走者を外す（出欠の変更、招待の取り消し、退会、走順の編集） | 走順。その後、メンバーの平均タイムとラップ数 | その大会のそのメンバーの `lap_records` を消す |
| 走順を変える | 走順 | `running_order_history` のスナップショット |

1 つ目の書き込みが成功した後に 2 つ目が失敗すると、2 つの DB が食い違う。例えば、走者は外れたのにラップが残り、平均タイムに数えられたままになる。これらはメンバーの記録に直接響くので、失敗しても黙って間違ったままにしてはいけない。ADR-0011 は順番と失敗時の扱いを実装に任せていた。この ADR は、そのすべてに共通するルールを 1 つ決める。

## Decision（決定）

**両方に書くユースケースは、残りの作業をまず PostgreSQL に記録し（outbox）、その作業はリクエストの中で、失敗したら再試行の仕組みが終わらせる。**

**手順**

1. **PostgreSQL の 1 つのトランザクション**で、そのユースケースの PostgreSQL の変更（あれば）**と、残りの手順を順に並べた outbox の行**を書く（例：大会 R のメンバー M のラップを消す、次に M の平均を計算し直す）
2. **MongoDB の手順**はコミットの後に動く。どれも冪等（2 回やっても 1 回と同じ結果）にする：
   - ドキュメントは、アプリが生成した ID（UUIDv7、`shared.IDGenerator`）で upsert する
   - 削除はキー（メンバーと大会）で行うので、もう一度消しても何も起きない
3. **最後の PostgreSQL の手順**（例：平均タイムの更新）は、**outbox の行を消すのと同じトランザクションで**行う。更新と行の削除が一緒にコミットされるので、再試行しても更新はちょうど 1 回だけ効く。`docs/design/database.md` の平均の式は変えない

**再試行**

- リクエストは、手順 1 の直後に手順 2 と 3 を実行する。失敗したら outbox の行が残る
- backend のプロセスの中の再試行の仕組みが、終わっていない outbox の行を、間隔を少しずつ空けながら拾う。行は `FOR UPDATE SKIP LOCKED` でロックするので、backend のプロセスが複数でも安全に動く
- 決めた回数だけ失敗したら、行は残したままエラーをログに出す（`log/slog`）。黙って捨てることはしない

**レスポンス**

- 手順 1 がコミットされたら、変更は受け付けたものとして API は成功を返す。手順 2 と 3 が終わるまで（ふつうは同じリクエストの中で終わる）、読み取りでは前の状態が見えることがある

**層（ADR-0011）**

- ユースケースは、Application の interface を通して outbox に書く。リポジトリへの書き込みと同じ作業単位（unit of work）で行う
- Infrastructure が outbox を PostgreSQL の表に保存し、MongoDB の手順と再試行の仕組みを動かす。PostgreSQL のトランザクションをリポジトリの間でどう共有するかは、DB へのアクセス（ADR-0015）と一緒に決める

## Alternatives considered（検討した他の案）

| 案 | 採用しなかった理由 |
| --- | --- |
| 順番だけ決め、失敗はログに出して手で直す | 失敗すると、誰かが気づくまで 2 つの DB が黙って食い違う。外れた走者のラップが平均に数えられ続ける |
| 2 つ目が失敗したら 1 つ目を取り消す（補償） | 取り消しも失敗しうるので、結局やり残しの記録が要る |
| ラップの記録と履歴を PostgreSQL に移す | 問題はなくなるが、追記型や文書の形のデータをリレーショナルなスキーマの外に置くという ADR-0002 の決定を覆す |
| 2 つの DB をまたぐ分散トランザクション | PostgreSQL と MongoDB の間ではできず、tasuki には重すぎる |

## Consequences（影響）

- MongoDB が一時的に使えなくても、2 つの DB は最終的に必ず揃う
- PostgreSQL に表（outbox）が 1 つ、backend に裏で動く仕組みが 1 つ増える。表は実装するときに `docs/design/database.md` に足す
- MongoDB の手順はすべて冪等に書き、最後の PostgreSQL の手順はすべて同じトランザクションで outbox の行を消す必要がある。レビューでこの 2 つを確かめる
- 成功を返した後の短い間、ほかの画面に前の状態（例：まだ更新されていない平均）が見えることがある。frontend は変更の後に取り直す（ADR-0013）ので、ふつうは見えない
- 失敗し続ける outbox の行は、誰かがログを見る必要がある。本番でそれにどう気づくかは、ホスティング（ADR-0018）と一緒に決める
