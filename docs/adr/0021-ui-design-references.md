# ADR-0021: UI design references — screens of shipped apps

- Status: Accepted
- Type: technical
- Date: 2026-11-08
- Issue: #145

## Context

`docs/design/screens.md` decides what each MVP screen shows and what it lets the user do. How the screens look is decided in #145 and its sub-issues: design basics (#146), common components (#147), and wireframes (#148). The UI sub-issues of #108 (#114, #120, #126, #132, #138, #144) are built from those.

Until now the screens are plain HTML without a design: each Container renders a plain UI so that it can be tested (ADR-0012), and the design comes with the UI sub-issues.

A design needs a starting point. Most of tasuki's screens do something that many apps already do: list upcoming events, answer attendance, invite and approve members, put people in an order, and show times. People who open tasuki already use apps like these, mostly on a phone inside LINE (ADR-0007).

Preferences about how tasuki looks are expected to change later. When that happens, it must be clear which parts of the design came from which reference and why, so that one part can be replaced without guessing.

## Decision

**We design the screens from the screens of shipped apps that do the same job, chosen per tasuki screen.** We do not start from designs generated by AI tools.

**References per screen**

| tasuki screen | Who uses it | Reference | What to take from it |
| --- | --- | --- | --- |
| R7 Running order editor | Organizer | TeamSnap: Lineups | Choose players from everyone or only from those who answered going, assign each an order or position, and keep it visible to admins until it is published |
| R6 Entry | Organizer | TeamSnap: Lineups, choosing from those who answered going | Offering only the members who answered attending as candidates |
| R3 Race form | Organizer | Spond: creating an event | Time, place, deadline, and who can see it on one form |
| R4 Invitations | Organizer | Spond: inviting to an event | Choosing who is invited to each event, and showing the event only to them |
| R5 Attendance | Organizer | Spond: the participant list | Changing a member's answer from the list, and reminding those who have not answered |
| R2 Lap times of runners | Organizer | Strava: splits and laps of a run | A table of times per lap or per km |
| M1 Roster | Organizer | Spond: "Invite to group with link"; Mobbin: the "Invite Teammates" pattern | Activating, copying, and sending an invite link |
| M3 Approvals | Organizer | Strava: "Pending Requests" of an invite-only club | Approving or declining each request one by one |
| M2 Member profile | Organizer | Strava: "Pace Analysis" | Showing the average next to the times of each part |
| R1 Race list | Member | Spond: the home screen | Events the member is invited to, listed on the home screen |
| R2 Attendance answer | Member | Spond: answering an event; Chouseisan (調整さん): ○△× | Answering from the event; Spond has only going and not going, so the three answers (attending, undecided, not attending) follow Chouseisan's ○△×, with the meaning of each answer written on the screen |
| R2 Confirmed running order | Member | TeamSnap: a published lineup | The order shared with the whole team once it is published |
| L1 My lap times | Member | Strava: laps and splits; Mobbin: Strava "Pace Analysis" | The table of times per lap. Strava takes times from devices, so the input itself needs another reference |
| P1 My profile | Member | Mobbin: Strava "Workout Stats" | Showing a few numbers large |
| A1 Invite landing | Before joining | Spond: requesting access with a group link or code | Requesting to join from a received link |
| A2 Waiting | Before joining | Strava: the waiting state of an invite-only club; Mobbin: Strava "Pending Invites" | What is shown while the request waits |
| A5 Login | Before joining | LINE Login button guidelines | The button's colors, shape, and wording, which LINE requires |

**How the references are used**

- We take the structure: what is on the screen, in which order, and where the main action is. We do not take colors, logos, illustrations, or wording.
- We look at phone screens only (iOS and Android), since tasuki is opened inside LINE on a phone.
- Where to look:
  - Strava: its screens on Mobbin, and Strava's help pages.
  - Spond: the app itself (free), used from both the admin and the member side, and Spond's help pages.
  - TeamSnap: Lineups is a paid feature in the iOS and Android apps, so its feature page, help pages, and App Store screenshots.
  - Chouseisan: the site itself.
- When a tasuki screen differs from its reference, `docs/design/screens.md` decides. For example, tasuki has three attendance answers where Spond has two.
- Colors, typography, and spacing are decided in #146, and the components in #147. This ADR does not decide them.

## Alternatives considered

| Option | Why it was not chosen |
| --- | --- |
| Start from designs generated by AI tools | The result is not tied to an app people already use, so nothing tells whether a layout is one they know. It also gives no reason that can be checked later when a part has to be replaced |
| Showcase sites (Dribbble, Behance) | Many works are made to look good as a picture, not to be used, and many are not phone screens |
| One app as the reference for every screen | No single app does all of tasuki: Spond and TeamSnap have no lap times, and Strava has no running order |
| A ready-made design system's look as it is (Material Design, Apple's Human Interface Guidelines) | They give rules for components and touch targets, not screens for attendance or running orders. They can still be used for those rules in #147 |

## Consequences

- Each screen's design has a written reason. When a preference changes, the screen and its reference can be found in the table above and replaced one at a time.
- A changed reference is recorded as a new ADR that supersedes this one, as for every ADR (`docs/adr/README.md`).
- Reviewing a design means comparing it with the reference in the table, instead of discussing taste alone.
- Two references are not on Mobbin: Spond has to be installed, and TeamSnap's Lineups can only be seen through its pages and App Store screenshots, since it is paid.
- Entering lap times on L1 has no reference yet. It is chosen in #148.
- The references are other companies' products. We copy their structure, not their visual design, so that tasuki does not look like any of them.

# ADR-0021: UI のデザインの参考 — 公開されているアプリの画面

- Status: Accepted
- Type: technical
- Date: 2026-11-08
- Issue: #145

## Context（背景）

`docs/design/screens.md` は、MVP の各画面に何を出し、何ができるかを決めている。画面の見た目は #145 とその sub-issue で決める：デザインの基本（#146）、共通の部品（#147）、ワイヤーフレーム（#148）。#108 の UI の sub-issue（#114、#120、#126、#132、#138、#144）は、それをもとに作る。

今の画面は、デザインのない素の HTML。各 Container はテストできるように素の UI を出していて（ADR-0012）、デザインは UI の sub-issue で入れる。

デザインには出発点が要る。tasuki の画面の多くは、たくさんのアプリがすでにしていることをする：これからの予定の一覧、出欠の答え、メンバーの招待と承認、人を順番に並べること、タイムの表示。tasuki を開く人は、こうしたアプリをすでに使っていて、多くはスマホの LINE の中から開く（ADR-0007）。

tasuki の見た目の好みは、後から変わると見込んでいる。そのとき、デザインのどの部分がどの参考から来たのか、なぜそれを選んだのかが分かっている必要がある。そうすれば、推測せずに一部だけを差し替えられる。

## Decision（決定）

**画面は、同じことをしている公開済みのアプリの画面をもとに、tasuki の画面ごとに参考を選んでデザインする。** AI のツールが作ったデザインから始めることはしない。

**画面ごとの参考**

| tasuki の画面 | 使う人 | 参考 | 取り入れること |
| --- | --- | --- | --- |
| R7 走順の編集 | 幹事 | TeamSnap：Lineups | 全員か「行く」と答えた人の中から選手を選び、順番や位置を割り当て、公開するまでは管理者だけに見せる |
| R6 エントリー | 幹事 | TeamSnap：Lineups の「行く人から選ぶ」 | 「参加」と答えたメンバーだけを候補に出す |
| R3 大会の登録 | 幹事 | Spond：イベントの作成 | 時刻、場所、締め切り、誰に見せるかを 1 つのフォームで決める |
| R4 招待 | 幹事 | Spond：イベントへの招待 | イベントごとに招待する人を選び、その人たちにだけイベントを見せる |
| R5 出欠の一覧 | 幹事 | Spond：参加者の一覧 | 一覧からメンバーの答えを直し、答えていない人に催促する |
| R2 走者のラップタイム | 幹事 | Strava：走った記録の Splits と Laps | 周回ごと、または 1 km ごとのタイムの表 |
| M1 名簿 | 幹事 | Spond：「Invite to group with link」、Mobbin：「Invite Teammates」の型 | 招待リンクを有効にし、コピーして送る |
| M3 承認 | 幹事 | Strava：招待制のクラブの「Pending Requests」 | 申し込みを 1 件ずつ承認するか断る |
| M2 メンバーのプロフィール | 幹事 | Strava：「Pace Analysis」 | 平均を、区間ごとのタイムと並べて出す |
| R1 大会の一覧 | メンバー | Spond：ホーム | 招待されたイベントをホームに並べる |
| R2 出欠の答え | メンバー | Spond：イベントへの答え、調整さん：○△× | イベントから答える。Spond は「行く」と「行かない」の 2 つだけなので、3 つの答え（参加、未定、不参加）は調整さんの ○△× にならい、それぞれの意味を画面に書く |
| R2 確定した走順 | メンバー | TeamSnap：公開された Lineup | 公開されたら、チーム全員に共有される順番 |
| L1 自分のラップタイム | メンバー | Strava：Laps と Splits、Mobbin：Strava「Pace Analysis」 | 周回ごとのタイムの表。Strava はタイムを機器から取るので、入力そのものには別の参考が要る |
| P1 自分のプロフィール | メンバー | Mobbin：Strava「Workout Stats」 | いくつかの数字を大きく出す |
| A1 招待リンクから入る | 参加前の人 | Spond：グループのリンクやコードで申し込む | 受け取ったリンクから参加を申し込む |
| A2 承認待ち | 参加前の人 | Strava：招待制のクラブの承認待ち、Mobbin：Strava「Pending Invites」 | 申し込みが待っている間に出すもの |
| A5 ログイン | 参加前の人 | LINE ログインのボタンのガイドライン | LINE が決めているボタンの色、形、文言 |

**参考の使い方**

- 取り入れるのは構造：画面に何があり、どの順に並び、主な操作がどこにあるか。色、ロゴ、イラスト、文言は取り入れない
- 見るのはスマホの画面（iOS と Android）だけ。tasuki はスマホの LINE の中で開かれるから
- 見る場所：
  - Strava：Mobbin にある画面と、Strava のヘルプ
  - Spond：アプリそのもの（無料）を、管理者とメンバーの両方の側から使う。Spond のヘルプ
  - TeamSnap：Lineups は iOS と Android のアプリの有料の機能なので、機能のページ、ヘルプ、App Store の画面写真
  - 調整さん：サイトそのもの
- tasuki の画面が参考と違うときは、`docs/design/screens.md` に従う。例えば、Spond の答えは 2 つだが、tasuki の出欠の答えは 3 つ
- 色、文字、余白は #146 で、部品は #147 で決める。この ADR では決めない

## Alternatives considered（検討した他の案）

| 案 | 採用しなかった理由 |
| --- | --- |
| AI のツールが作ったデザインから始める | 人がすでに使っているアプリと結びついていないので、その配置が慣れたものかどうかが分からない。一部を差し替えるときに、後から確かめられる理由も残らない |
| 作品を見せるサイト（Dribbble、Behance） | 使うためではなく、絵として良く見えるように作った作品が多く、スマホの画面でないものも多い |
| 1 つのアプリを全画面の参考にする | tasuki のすべてをするアプリはない。Spond と TeamSnap にはラップタイムがなく、Strava には走順がない |
| 既存のデザインシステムの見た目をそのまま使う（Material Design、Apple の Human Interface Guidelines） | 部品や押せる範囲の決まりはあるが、出欠や走順の画面はない。その決まりは #147 で使える |

## Consequences（影響）

- 各画面のデザインに、書き残した理由がある。好みが変わったら、上の表で画面と参考を見つけ、1 つずつ差し替えられる
- 参考を変えたら、ほかの ADR と同じく、これを置き換える新しい ADR に書く（`docs/adr/README.md`）
- デザインのレビューは、好みだけで話すのではなく、表の参考と比べて行う
- 2 つの参考は Mobbin にない。Spond はアプリを入れる必要がある。TeamSnap の Lineups は有料なので、ページと App Store の画面写真でしか見られない
- L1 でラップタイムを入力する部分には、まだ参考がない。#148 で選ぶ
- 参考は他社の製品。見た目ではなく構造を取り入れるので、tasuki はどれとも似た見た目にはならない
